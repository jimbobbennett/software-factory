**Correctness.** Does the change do what the spec says, for every acceptance criterion? Check edge cases (empty, missing, huge, unicode, timezones), error handling, behaviour changes for existing callers, and whether the change is the smallest one that works. Flag workarounds that hide a problem instead of fixing it, such as a `noqa`, a broad `except`, or a hardcoded value.

**Spec goals are in scope.** The spec includes its stated goals, reasons and assumptions ("we need X so that Y", "Y also counts as Z"), not only the numbered criteria. For each one, confirm that the code after the merge actually produces it. Follow new or extra data all the way to the specific output the spec says it affects. Finding some consumer is not enough. If the code doesn't make a stated goal or assumption true, that is a **major** finding against this PR, even if the gap is in code the PR didn't touch. Never mark something as "out of scope", "pre-existing" or a "note" and then approve when the spec relies on it. Raise it as major. The fix can be to change the code or to revise the spec.

**Every branch of a changed function.** When a function gains or changes a parameter, read every branch in its body: early returns, `if client` / `if cache` / default-value paths, and fallbacks. Check each branch, including ones no current caller uses, because the function's signature and docs are its contract. In your summary, list each branch in one line and say whether the new value is applied there. If a value the caller passes explicitly is silently ignored on any branch, that is a **major** finding.

**Verdict.** If you write down a mismatch between the spec and the code, it must appear as a finding with a severity, not only in the summary prose. Approve only when every criterion, goal and assumption holds on every branch. Still approve correct PRs. Don't block on style, hypothetical inputs the spec doesn't care about, or issues in other lanes.
