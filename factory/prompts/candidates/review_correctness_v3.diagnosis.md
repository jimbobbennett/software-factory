There were two different failures, and v2 only went after one of them. (1) The reviewer saw the problem and still approved. In the pagination PR under v1, the reviewer noticed that the spec says "reviewers are crew" and that the crew code never reads reviews, then called this "out of scope" and approved. That is a verdict-calibration failure. Under v2, the "follow the data" check stopped at the first consumer it found (the reviewer count) and never asked whether the outcome the spec promised actually happens. Neither version said that the spec's stated assumptions and goals are in scope, or that the PR fails if those assumptions are false in the code. (2) The reviewer didn't check every branch of the changed function. In the token PR, both versions traced the token only along the paths that real callers use today. Neither checked the branch inside the function where an injected client skips the new parameter. v2 asked for a check of "every combination" but required no written evidence, so the reviewer could write "every way it can be called works" without listing a single branch. v2 got the same result as v1 because it added more "look harder" instructions, didn't remove the out-of-scope escape, and asked for no visible proof that the checks were done. The fix: treat spec goals and assumptions as in scope and major when they are unmet, ban the "out of scope, approve anyway" pattern, require a one-line-per-branch list in the summary, and require any mismatch the reviewer writes down to become a finding with a severity.
